# Часть 1. API и DX глазами обычного разработчика

## Что честно подкупает

Чтобы критика ниже читалась в правильном контексте — сначала то, что сделано на уровне выше рынка:

- **Порог входа на первой странице реально низкий.** `state(0)` → `.set` / `.update` → `{count}` в JSX. Счётчик от React отличается на три строки. Скаффолд, `jsxImportSource`, тест в комплекте — онбординг за минуты.
- **Сообщения об ошибках — обучающие.** `requireScope` не просто ругается, а показывает `root(() => …)` с примером. Ошибка rank overflow объясняет, что такое временной цикл и чем его разорвать. Это редкость.
- **Документация — сильнейшая сторона.** from-react с таблицей соответствий, from-rxjs, common-mistakes (честный список собственных футганов), patterns-кулинарная книга, интерактивный туториал с проверками. Мало какой фреймворк такое имеет на старте.
- **Типизация JSX** — `Reactive<T>`, `EventHandler` с конкретным `currentTarget`, вывод атрибутов из DOM-интерфейсов — продумана.
- **Ядро держит свои законы.** Транзакции, ранги, boundary-commit — движок сам подчиняется дисциплине, которую навязывает пользователю. Это видно в коде и это фундамент всех «нечестных преимуществ» (undo/replay/sync одной свёрткой).

Теперь — адверсариально.

## К1. JSX выглядит как React, но молча ведёт себя иначе — худший класс футганов

Самая опасная категория: код **компилируется, работает при первом рендере и тихо устаревает**. Обычный разработчик перенесёт из React привычки, и каждая из них — мина:

| Привычка из React                                | Что происходит в Continuum                                            | Как узнаёшь                   |
| ------------------------------------------------ | --------------------------------------------------------------------- | ----------------------------- |
| `{cond ? <A/> : <B/>}`                           | вычислено один раз, никогда не переключится                           | молча                         |
| `{count.sample()}` (аналог `count` как значения) | статический текст навсегда                                            | молча                         |
| `<Show when={user}>{u => u.name}</Show>`         | `u` — снапшот; смена userA→userB (оба truthy) **не обновляет** детей  | молча (**проверено, см. Б3**) |
| `<Each>` со списком плоских объектов             | строка с выжившим ключом **не обновляется** при изменении полей       | молча (**проверено, см. Б4**) |
| `<Catch><Risky/></Catch>`                        | JSX жадный — throw случится **до** того, как Catch получит управление | ошибка мимо boundary          |

Common-mistakes честно документирует №1, №3, №4 — но документированный футган остаётся футганом. Это структурная проблема «знакомого синтаксиса с незнакомой семантикой»: чем более знакомо выглядит, тем меньше пользователь ждёт подвоха.

**Смягчение возможно на трёх уровнях** (см. предложения П1–П3): семантические фиксы (`Show`/`Each` могут отдавать живые значения), lint-правила (тернарник с JSX-ветками внутри JSX, `.sample()` в JSX детях — оба ловятся статически), и type-уровень (`Catch` мог бы принимать **только** thunk).

## К2. Правило владения непредсказуемо снаружи модели

Внутреннее правило чистое: _источники и формулы не нуждаются во владельце, процессы (stateful-деривации и эффекты) — нуждаются_. Но снаружи, не зная модели, невозможно угадать:

- `state(0)` на уровне модуля — работает;
- `clicks.accum(0, f)` на уровне модуля — throw;
- `clicks.map(f)` — работает;
- `debounce(clicks, 300)` — работает… и **утекает навсегда** (см. Б1 — std вообще не участвует в модели владения).

То есть пользователь наблюдает четыре разных поведения там, где видит четыре однотипных вызова. Ошибка `requireScope` — лучшая в своём классе, но сама необходимость выучить классификацию «источник/формула/процесс» до того, как заработает счётчик кликов — налог на вход. Хуже то, что **std нарушает правило молча** — это уже баг-класс (Часть 2, Б1), но и DX-урон: доверие к правилу подрывается там, где оно молча не работает.

## К3. Модель моментов протекает в трёх местах, где новичок не ждёт

Boundary-commit — принципиальное решение, и вне `batch` оно почти невидимо (`set` вне транзакции коммитится синхронно — молодец). Но:

1. `batch(() => { a.set(5); a.sample(); })` → старое значение. `update()` видит staged, `sample()` — нет. Два способа прочитать, два разных ответа внутри одного batch.
2. `draft.at(submits)` видит значение _до_ момента — common-mistake №6 существует потому, что интуиция ломается.
3. `set(sample() + 1)` дважды в batch — не компонуется (документировано, но это ловушка «работало вне batch — сломалось внутри»).

Предложение не «сломать модель», а сузить поверхность: **`sample()` внутри активной транзакции в dev-режиме мог бы предупреждать** («вы читаете pre-moment значение; хотели pending? — используйте `update`»). Одна dev-проверка убирает целый класс тихих недоумений.

## К4. Контракт компонентов: `Reactive<T>` без инструментов

Props компонента могут быть `T` или `State<T>` — но автору переиспользуемого компонента не дали ничего:

```tsx
function Badge(props: { label: Reactive<string> }) {
  // единственный способ:
  const label =
    props.label instanceof State ? props.label : constant(props.label);
}
```

Нет `asState()`, нет аналогов `mergeProps`/`splitProps` (дефолты для props руками через `??` — а если prop это State?), нет helper'а для children. Solid прошёл этот путь и знает, что без таких утилит экосистема компонентных библиотек не заводится. Сейчас писать «библиотечный» компонент на Continuum ощутимо больнее, чем прикладной код.

## К5. Поверхность API: удвоение, разнобой имён, потолки

- **Двойной API** `when/Show`, `dyn/Dynamic`, `each/Each`, `portal/Portal` — «симметрия» удваивает то, что нужно выучить и задокументировать. Симметрия — аргумент авторов; пользователь видит два способа сделать одно и то же и спрашивает, какой правильный.
- **`distinct` (frp, для Stream) vs `dedupe` (std, для State)** — одна концепция, два имени, к тому же в dom есть третья приватная реализация (единственная корректная из трёх — см. Б1).
- **`accumE`** — соди́умный жаргон; суффикс E ничего не говорит человеку без FRP-бэкграунда. `at` — лаконично, но недискавируемо (поиск «snapshot continuum» найдёт больше, чем «at»); при этом сообщение об ошибке в ядре до сих пор говорит «snapshot» (Б14).
- **`combine` ограничен 5 аргументами**, а для динамических коллекций (`State<Item[]>`, у каждого item свой `State<number>` цены → total) нет вообще ничего — ни `combine(array)`, ни `joinAll(State<State<T>[]>)`. Это не экзотика, это «итого корзины» — вторая страница любого приложения. Сейчас решается ручной связкой map+flatten, которую новичок не выведет.
- **`Stream.merge(a, b, f)` как статика** — на фоне остального fluent-API выбивается; `a.or(b)` есть, а `a.merge(b, f)` нет.

## К6. Router — прототип, продающийся рядом с production-ядром

Ядро роутера концептуально красивое (URL как State, уровень = dyn-регион, идентичность маршрута против rebuild). Но по чек-листу реального приложения:

- **`Link` не пробрасывает произвольные props** — нельзя передать `target`, `rel`, `aria-label`, `data-*`, `id`. Типы это запрещают, рантайм игнорирует. Любая ссылка сложнее «текст + класс» — тупик.
- Нет `aria-current="page"` на активной ссылке (a11y — это то, что аудиторы проверяют первым).
- **Параметры не декодируются**: `/users/John%20Doe` → `params.id === "John%20Doe"` (Б8).
- Активность `Link` сравнивает только `pathname` — href с `?query` не бывает активным.
- Guards синхронные и видят только params — ни URL, ни async-проверку сессии не выразить.
- Нет search-params-хелпера (URL есть, но каждый парсит `u.searchParams` сам и без dedupe — каждый keystroke в несвязанной части URL дёргает подписчиков).
- Нет base path (деплой под `/app/` невозможен), нет hash-режима, повторный `navigate` на тот же URL пушит дубль в history.
- `lazy` без дедупликации параллельных загрузок одного чанка.

Плюс роутер построен на std-`dedupe` и **утекает на каждую навигацию** (Б1 — самое практическое следствие всей утечной семьи).

## К7. std: минимализм местами переходит в «нельзя пользоваться всерьёз»

- **`resource`** — правильная идея (async lifecycle как данные, last-request-wins), но: нет abort (проигравший fetch продолжает жечь сеть), нет `refetch`, нет initial data, и **гонка на ветке ошибок реально не решена** (Б2, проверено). Слоган «race-free search» сейчас неточен.
- **`bindInput`** — только `string`. Checkbox, number, select, radio — руками. Forms-трек туториала это обходит, но обычный разработчик ждёт `bindChecked`/`bindNumber` рядом.
- `throttle` без trailing-опции; `interval` без немедленного тика; `type()` в test-пакете только дописывает символы (нет «очистить и ввести»).

## К8. Экосистемные дыры, которые заметит любой evaluating-разработчик

Не баги, но именно на этом чаще всего заканчивается evaluation:

1. **Нет devtools** — при том, что «граф виден по построению» — заявленное нечестное преимущество. Сейчас при неожиданном поведении у пользователя нет вообще ничего: ни графа, ни лога транзакций, ни счётчика подписок (утечки из Б1 невозможно увидеть штатными средствами!).
2. **Нет SSR/гидрации** — для многих команд это фильтр на входе.
3. **HMR теряет состояние** (а модель позволяет честнее, чем Fast Refresh — это даже в 4EPUHA замечено).
4. Нет компонентных библиотек / headless-примитивов — и без утилит из К4 они не появятся.

## Предложения по улучшению (по приоритету)

### P0 — до любого следующего релиза

- **П1. Починить модель владения в std** (это Б1): чистые шейперы (`filterMap`) — на ленивый `source()`; stateful (`pairwise`, `dedupe`) и таймеры (`debounce`/`throttle`/`delay`/`interval`) — `requireScope`, как `perform`. Каноническую ленивую реализацию `dedupe` (она уже написана — приватная в dom) поднять в frp-ядро, dom и std используют её.
- **П2. `resource`: штамповать seq и на ошибках** (Б2) + прокидывать `AbortSignal` в fetcher.
- **П3. `Show`/`Each` — отдать живые значения**: `<Show keyed>` (rebuild по референсу) или children-аргумент `State<NonNullable<T>>`; в `each` при реюзе строки обновлять per-row cell и передавать его в render. Минимум — кричащий разворот в docs + lint.

### P1 — DX-рычаги с максимальным отношением эффекта к стоимости

- **П4. Утилиты компонентного автора**: `asState(v: Reactive<T>): State<T>`, `withDefaults(props, defaults)`, типизированный helper для children. Это разблокирует библиотеки.
- **П5. `combine(states: State<T>[], f)`** (массивная перегрузка без потолка арности) и **`joinAll(State<State<T>[]>): State<T[]>`** — закрыть «итого корзины».
- **П6. Три lint-правила**: тернарник/`&&` с JSX-ветками внутри JSX-выражения; `.sample()`/`.sampleNoTrans()` в JSX-детях; std-таймер вне scope (пока П1 не сделан). Ловятся тривиально, убирают 80% тихих футганов из К1.
- **П7. Dev-warning на `sample()` внутри активной транзакции** (К3).
- **П8. Router до production-чеклиста**: спред-props у `Link` + `aria-current`, `decodeURIComponent` params (Б8), `useSearchParams()` с dedupe, base path, async guards. Каждый пункт — маленький; вместе — «можно брать».

### P2 — стратегическое

- **П9. Devtools-минимум**: оверлей со счётчиком живых узлов/подписок (сразу ловит утечки класса Б1), лог транзакций (flight recorder — из 4EPUHA, и это честное преимущество модели). Даже консольный `debugGraph()` уже поменял бы evaluation.

# Часть 2. Аудит кода на баги

Все находки Б1–Б5 **воспроизведены тестами** на текущей ветке (vitest + jsdom); остальные подтверждены чтением кода. Сортировка по убыванию серьёзности.

## Б1. [~~High~~ → Medium, см. Ревизию v2] std игнорирует модель владения: утечки подписок, зомби-таймеры; router утекает на каждой навигации

**Где:** `packages/std/src/index.ts` — `dedupe` (:153), `filterMap` (:96), `pairwise` (:108), `debounce`/`throttle`/`delay`/`interval` (:18–:84).

**Механизм.** Ядро строго делит узлы на ленивые рецепты (`source()` — подписка при первом слушателе, отписка после последнего) и scoped-процессы (`requireScope` + `scope.onDispose(un)`). std не делает ни того, ни другого:

- `dedupe`: `b.updates.listen_(out, h)` — **немедленная** подписка, unlisten-хендл **выброшен**. Отписаться невозможно в принципе: `out.dispose()` чистит только собственные attachments узла, а этот edge живёт в `obs` источника.
- `filterMap`/`pairwise`: `out.consume(e, h)` — тоже немедленная подписка; cleanup сработал бы на `dispose()`, который никто никогда не вызывает (и не должен — нигде в модели пользователь не обязан звать dispose руками).
- `debounce`/`throttle`/`delay`/`interval`: `e.listen(...)` + таймеры, привязка к scope отсутствует. `interval` в компоненте = setInterval, который **никогда не остановится** после unmount; `debounce` продолжает слушать источник и жечь таймеры.

**Репро (прогнано, зелёное):**

```ts
const s = state(1);
for (let i = 0; i < 10; i++) dedupe(s); // +10 постоянных edge на s.updates
// dispose() возвращённых стейтов не убирает ни одного
```

**Практическое следствие — router.** `renderLevel` и `useParams` создают std-`dedupe` при каждой сборке уровня/компонента. Каждая навигация, меняющая def уровня, оставляет навсегда живую цепочку map+dedupe, подписанную (транзитивно) на location-cell: **неограниченный рост памяти и CPU-работы на каждый route change в любом приложении с роутером**. Проверено на уровне механизма (счётчик edges растёт, dispose не помогает).

**Ирония:** в dom лежит третья, приватная реализация dedupe (`packages/dom/src/index.tsx:860`) — ленивая, с `onWake`-reseed, полностью законопослушная. Каноническое решение уже написано.

**Фикс:** П1 из части 1. Плюс系统ное: прогнать все std/router-комбинаторы через чек-лист «два закона» (формула → `source()`; процесс → `requireScope`); это же — кандидат в CONTRIBUTING.

## Б2. [~~Medium-High~~ → Medium] `resource`: ошибка вытесненного запроса затирает состояние актуального

**Где:** `packages/std/src/index.ts:192-204`.

Seq штампуется только на успех (`.then(value => ({seq, value}))`); rejection летит в `perform` без seq, и ветка ошибки в `settled` **не сверяет** `latestSeq`:

```ts
if (res.ok) { if (res.value.seq !== latestSeq) return null; ... }
return { status: "error", error: res.error };   // ← любой fail, даже устаревший
```

**Репро (прогнано):** fire(1); fire(2); reject первого → `res.sample().status === "error"`, хотя актуальный запрос №2 ещё loading. Классическая гонка, которую resource заявляет решённой, — жива на error-ветке. UI покажет пользователю ошибку от запроса, который тот уже «перебил» новым вводом.

**Фикс:** штамповать seq в обе ветки (`run(a).then(v => ({seq, value: v}), e => Promise.reject({seq, error: e}))` + разбор в settled), заодно try/catch вокруг синхронного `fetcher` (Б9).

## Б3. [~~Medium~~ → отозвано как баг; DX-ловушка] `Show`: дети устаревают при truthy→truthy смене значения — включая пример из собственного docstring

**Где:** `packages/dom/src/index.tsx:1004-1016`.

`when(present, …)` ребилдит только при смене истинности; children получают **снапшот** `props.when.sample()` на момент сборки.

**Репро (прогнано):** `user.set({name:"Grace"})` при живом `{(u) => <span>{u.name}</span>}` → на экране остаётся «Ada». Пример в docstring `Show` — ровно этот код.

**Фикс:** П3 (keyed-режим или `State<NonNullable<T>>` в children). Минимум — предупредить в docstring и docs, что children-аргумент — снапшот, живые поля брать из исходного стейта.

## Б4. [~~Medium~~ → отозвано как баг; DX-ловушка] `each`: строка с выжившим ключом никогда не обновляется при изменении данных

**Где:** `packages/dom/src/index.tsx:737-738` (`next.push(rows[prevIdx]); // reuse: no re-render`).

**Репро (прогнано):** `items.set([{id:1,name:"B"}])` после `[{id:1,name:"A"}]` → рендерится «A». Для fine-grained модели это «так задумано» (данные строк должны быть стейтами), но: (а) типичный источник — сервер, отдающий свежие плоские JSON-массивы; (б) React-переселенец получает молчаливо неверный UI. Solid решает это `mapArray`-семантикой; здесь эквивалента нет.

**Фикс:** П3 — при реюзе строки писать новый item в per-row cell и передавать `State<T>` в render (opt-in вторым аргументом children, чтобы не ломать текущий контракт). Дополнительно: дубликаты ключей сейчас молча схлопываются (:734) — стоит dev-warning.

## Б5. [~~Medium~~ → Low] `combine` поверх непрерывного стейта эмитит значения, замороженные на момент wake

**Где:** `packages/frp/src/index.ts:1075-1085` (lift2 `flush` использует кэш `va`/`vb` для не-обновлявшегося входа).

Для дискретных стейтов кэш эквивалентен `sampleNoTrans()` (коммиты на границе). Для continuous (`time()`, `State.fromPoll`) — нет: у них пустой updates, кэш заполняется только на wake и **замерзает навсегда**, пока узел тёплый.

**Репро (прогнано):** `combine(fromPoll(() => now), x, (t) => t)`; после wake `now=100`; двигаем `now=200`, `x.set(1)` → push-подписчик получает **100**, `sample()` говорит **200**. Прямое нарушение закона «push и pull видят одно и то же» (FRP-MODEL) — той же природы, что открытые #135/#113, но в стационарном (не aborted) режиме.

**Фикс:** в `flush` для входа без staged-значения читать `sampleNoTrans()` вместо кэша — для дискретных это то же значение (pre-moment), для continuous — корректное свежее; кэши остаются только как fallback/оптимизация, если сэмпл дорог. Либо честно задокументировать «combine поверх continuous — только pull».

## Б6. [~~Medium~~ → Low-Medium/perf, измерено] Квадратичный teardown дерева scope'ов

**Где:** `packages/frp/src/index.ts:73-96`.

`dispose()` родителя обходит детей с конца; каждый ребёнок в своём `dispose()` ищет себя `siblings.indexOf(this)` — скан с начала массива. Для n детей — Σi ≈ n²/2 сравнений. 10k строк each → ~5·10⁷ операций на clear. На бенчмарке «clear 1000» (n²/2 = 5·10⁵) это незаметно, на 10k — уже миллисекунды впустую.

**Фикс (однострочный):** родитель ставит `flags |= 1` **до** обхода детей — ребёнку достаточно пропустить splice, если `this.parent.disposed`.

## Б7. [Low-Medium] Enumerated-атрибуты ломаются на `false`

**Где:** `packages/dom/src/index.tsx:345-348` (`setProp`).

`typeof value === "boolean" && !value → removeAttribute`. Но у `draggable`, `spellcheck`, `contenteditable`, `translate`, `autocapitalize` значение `"false"` **семантически отличается** от отсутствия атрибута: `<div draggable={false}>` должен дать `draggable="false"`, а получает дефолт (auto). React ведёт для них отдельный список — здесь нужен такой же маленький Set исключений.

## Б8. [Low-Medium] Параметры маршрута не URL-декодируются

**Где:** `packages/router/src/match.ts` (`params[own[i].slice(1)] = segs[i]`).

`/users/John%20Doe` → `useParams().id === "John%20Doe"`. Любой параметр с пробелом/юникодом/слэшем доедет закодированным; сравнения и вывод в UI дадут мусор. Фикс: `decodeURIComponent` в try/catch (malformed — оставить как есть).

## Б9. [Low] `perform`: синхронный throw из `run` минует Result-контракт

**Где:** `packages/frp/src/index.ts:1662`.

Контракт — «errors flow as data», но если `run(a)` бросает **до** возврата промиса (битый URL, JSON.stringify циклической структуры), throw происходит в observer-фазе и перебрасывается из `fire`, вызвавшего запрос — падает совершенно посторонний код. Фикс: try/catch вокруг `run(a)` → `fire({ok:false, error})`.

## Б10. [Low] Любой prop `on*` считается событием

**Где:** `packages/dom/src/index.tsx:459` (`key.length > 2 && key.startsWith("on")`).

Атрибут/prop с именем на `on`, не являющийся событием (custom element с prop `onto`, `once`), молча уйдёт в `addEventListener("to", …)`. Экзотика, но проверка по известному множеству (или `on` + заглавная буква) дешёвая.

## Б11. [~~Low~~ → nit] Ref-объект не обнуляется на unmount

`applyRef` пишет `ref.current = el` и никогда не сбрасывает — после dispose ref держит мёртвый элемент (mini-утечка + ложное «элемент есть»). React обнуляет; здесь достаточно cleanup'а в `applyProp`.

## Б12. [Low] Мелочи делегирования событий

`packages/dom/src/index.tsx:393-410`: (а) `Object.defineProperty(e, "currentTarget")` остаётся на объекте события после диспатча — код, читающий event позже (логгеры), увидит последний узел; (б) `stopImmediatePropagation` не поддержан; (в) Shadow DOM: walk по `parentNode` не ретаргетится через `composedPath()` — хендлеры внутри shadow root недостижимы. Контракт «как у Solid» — но стоит задокументировать все три пункта.

## Б13. [Low] `h(Component, {children: …})` затирает children пустым rest-массивом

`packages/dom/src/index.tsx:508`: `{...(props||{}), children}` — при ручном вызове `h(Comp, {children: x})` без rest-детей props.children станет `[]`. Automatic runtime не задет; чинится проверкой `children.length`.

## Б14. [Trivial] Сообщение об ошибке ссылается на несуществующее API

`makeFire` (:1232): «…(map/filter/**snapshot**/accum)» — `snapshot` переименован в `at` (в `Cell.write` уже поправлено). Копеечный фикс, но именно такие ошибки читают в самый напряжённый момент.

## Б15. [Model — НЕ ПРОВЕРЕНО] Проглоченный throw внутри `batch` коммитит полумомент

`batch(() => { try { fire(x) } catch {} fire(y) })`: throw на середине push-цепочки оставляет часть узлов застейдженными; batch завершается нормально — граница коммитит **частично распространённое** состояние (push/pull-дивергенция той же семьи, что #135). Модель «аборт = момент не был» работает, только если throw доходит до `Transaction.run`. Стоит либо помечать транзакцию tainted при escape из send-цепочки, либо явно задокументировать «не ловите исключения поверх fire внутри batch».

## Связь с открытыми issues

- **#118** (switchB phase-2 эмиссия → глитч в join) и **#135** (stale-кэши после аборта) — подтверждаю прочтением: та же phase-2-семья, что и reseed-эмиссия `lift2` (`out.send_` внутри вложенного `t.last`, index.ts:1133) — она рассылает в фазе 2 и точно так же может дать второй flush нижележащему join'у в том же моменте. Правильно чинить все три одним механизмом: **любая пост-rewire/reseed эмиссия идёт через rank-ordered `t.prioritized`** (как предложено в issue-треде #118), фаза 2 оставляет только коррекцию.
- Б5 — третий член той же серии «push расходится с pull», но в стационарном режиме; чинится независимо и проще всех.

## Системный вывод по коду

Ядро (`frp/index.ts`) — выдающегося качества: законы сформулированы, машинно соблюдаются, каждая оптимизация обоснована комментарием с профилем. **Все серьёзные баги — на периферии (std, router, dom-хелперы), и почти все — одного корня: периферия не была прогнана через законы ядра.** Это хорошая новость: нужен не редизайн, а один проход «law-compliance» по std/router (П1) плюс точечные фиксы Б2–Б8. Плохая новость: два самых видимых пользователю дефекта (утечка на навигации, гонка ошибок ресурса) живут именно в том слое, который обычный разработчик трогает первым.
