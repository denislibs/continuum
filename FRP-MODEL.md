# Модель FRP в Continuum: операционный разбор

Это второй из двух концептуальных документов репозитория, и они намеренно
смотрят на одно и то же с разных сторон:

- [PHILOSOPHY.md](PHILOSOPHY.md) — **денотационная** сторона: что типы
  _означают_ математически (линия Конала Эллиотта, Fran).
- этот файл — **операционная** сторона: как дискретная машина честно
  приближает эту математику — транзакции, задержка `hold`, ранги, `switch`.

Операционная линия у нас — из книги Stephen Blackheath & Anthony Jones,
**«Functional Reactive Programming»** (Manning, 2016;
[manning.com/books/functional-reactive-programming](https://www.manning.com/books/functional-reactive-programming)),
описывающей систему **Sodium**. Ядро `@continuum-js/frp` — реализация именно
этой дискретной ветви классического FRP, поэтому почти каждый раздел ниже
снабжён отсылкой к главе книги. Дальше — «книга», «гл. N».

Все примеры кода — работающий Continuum (TypeScript), не псевдокод.

## 1. Зачем всё это: шесть бедствий обработчиков событий

Книга начинается (гл. 1) не с определения FRP, а с диагноза: почему код на
слушателях/колбэках гниёт. Авторы перечисляют «шесть бедствий» (six plagues)
событийного кода — вот они, в переводе на язык фронтенда:

| Бедствие                   | Как выглядит в жизни                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------- |
| Непредсказуемый порядок    | два обработчика одного клика, результат зависит от порядка подписки                    |
| Пропущенное первое событие | подписался позже, чем случилось; «а прогрузилось ли уже?»                              |
| Грязное состояние          | флажки `isLoading`, `hasClicked`, рассыпанные по замыканиям                            |
| Угроза многопоточности     | в JS — реэнтерабельность: обработчик дёргает `setState`, тот дёргает другой обработчик |
| Утёкшие колбэки            | забыл `removeEventListener` — объект жив вечно                                         |
| Случайная рекурсия         | обновление A триггерит B, B — снова A                                                  |

FRP по книге — не «стримы с сахаром», а дисциплина, при которой этих бедствий
_не может возникнуть по построению_. Раздел 10 ниже показывает, каким именно
механизмом закрывается каждое.

## 2. Словарь: Sodium ↔ Continuum

Книга использует имена Sodium. Continuum использует имена ветви
Behaviors/Streams (как во Fran и ранних статьях Эллиотта). Таблица соответствия
— чтобы читать книгу с нашим API под рукой:

| Sodium (книга)              | Continuum                             | Что это                           |
| --------------------------- | ------------------------------------- | --------------------------------- |
| `Cell<A>`                   | `Behavior<A>`                         | значение во времени (всегда есть) |
| `Stream<A>`                 | `Stream<A>`                           | дискретные происшествия           |
| `CellSink` / `StreamSink`   | `newBehavior(init)` / `newStream()`   | вход в граф извне                 |
| `stream.hold(init)`         | `e.hold(init)`                        | ступенчатая функция из событий    |
| `stream.snapshot(cell, f)`  | `e.snapshot(b, f)`                    | снять значение в момент события   |
| `stream.map` / `filter`     | `e.map` / `e.filter`                  | как везде                         |
| `stream.merge(other, f)`    | `Stream.merge(ea, eb, f)`             | слияние с коалесингом             |
| `stream.orElse(other)`      | `e.orElse(other)`                     | лево-приоритетное слияние         |
| `stream.gate(cell)`         | `e.gate(b)`                           | пропускать, пока behavior истинен |
| `stream.accum(init, f)`     | `e.accum(init, f)`                    | свёртка в behavior                |
| `stream.once()`             | `e.once()`                            | только первое происшествие        |
| `cell.map`, `lift`          | `b.map`, `Behavior.lift2/lift3/apply` | поточечные операции               |
| `cell.sample()`             | `b.sample()`                          | операционное чтение               |
| `Operational.updates(cell)` | `b.updates`                           | дискретные изменения behavior     |
| `Operational.value(cell)`   | `b.listen(h)`                         | текущее значение + изменения      |
| `Cell.switchC(cc)`          | `Behavior.switchB(bb)`                | следовать за выбранным behavior   |
| `Cell.switchS(cs)`          | `Behavior.switchE(be)`                | следовать за выбранным event      |
| `calm` (паттерн, гл. 12)    | `distinct(e)` / `distinctB(b)`        | гасить повторы значений           |
| `listen`                    | `e.listen(h)`                         | люк наружу: колбэк после момента  |
| — (в Sodium нет)            | `perform(e, run)`                     | IO-граница с `Result` как данными |

Книга насчитывает **десять первичных примитивов** (гл. 2 + `switch` из гл. 7):
`never`, `constant`, `map`, `merge`, `hold`, `snapshot`, `filter`, `lift`,
`sample`, `switch`. Всё остальное — производные. В Continuum это ровно так же:
например, `accum` внутри ядра собран из `hold` + `snapshot`-подобного чтения
([`packages/frp/src/index.ts:283`](packages/frp/src/index.ts)), а `orElse` —
частный случай `merge`.

## 3. Транзакция = момент времени

Центральное операционное понятие книги: всё, что происходит, происходит
_внутри транзакции_ (в книге и у нас — «момент», moment). Транзакция — это
не блокировка и не батчинг ради производительности, а **реализация
одновременности**: у дискретного времени есть атомарные мгновения, и всё, что
случилось в одном мгновении, случилось _одновременно_ — без «чуть раньше»
внутри.

```ts
import { newStream, Stream } from "@continuum-js/frp";

const [click, fireClick] = newStream<void>();
const a = click.mapTo("a");
const b = click.mapTo("b");
const both = Stream.merge(a, b, (l, r) => l + r);

both.listen(console.log);
fireClick(); // печатает "ab" — ОДНО происшествие, не два
```

Без транзакций `both` выстрелил бы дважды («глитч» — наблюдаемое
промежуточное состояние). С транзакциями `merge` знает, что `a` и `b`
одновременны, и коалесцирует их в одно происшествие комбинирующей функцией.
Это поведение `merge` из гл. 2 книги — там подчёркивается, что вариант «два
отдельных выстрела» был бы _семантически неверен_, потому что в денотации
`Stream a ≅ [(Time, a)]` не бывает двух происшествий в одно время в одном
событии.

### Три фазы момента

Транзакция Continuum исполняется в три фазы
([`packages/frp/src/index.ts:20`](packages/frp/src/index.ts)):

1. **prioritized** — протяжка по графу в порядке рангов (см. ниже);
2. **last** — коммиты на границе момента: сюда откладывают запись `hold` и
   перекоммутацию `switch`;
3. **post** — наблюдатели (`listen`): исполняются, когда момент уже закрыт,
   поэтому `fire` из наблюдателя открывает _новый_ момент, а не вкладывается
   в текущий.

### Ранги: почему нет глитчей в ромбе

Классическая проблема ромба (diamond): `d = f(b, c)`, где и `b`, и `c`
зависят от `a`. Наивный push вычислит `d` дважды за момент, один раз — со
смешанным (старым/новым) состоянием. У нас у каждого узла есть **ранг** —
топологическая высота в графе; работа внутри момента исполняется min-кучей в
порядке рангов, а `lift2`/`merge` планируют себя _один раз_ за момент на своём
ранге:

```ts
import { newBehavior, Behavior } from "@continuum-js/frp";

const [n, setN] = newBehavior(1);
const doubled = n.map((x) => x * 2); // ранг 1
const squared = n.map((x) => x * x); // ранг 1
const sum = Behavior.lift2((d, s) => d + s, doubled, squared); // ранг 2

sum.updates.listen(console.log);
setN(3); // печатает 15 — ровно один раз, никогда 7 или 11
```

`lift2` собирает оба входа в фазе prioritized и «прошивает» наружу одно
обновление. Ранг поддерживается инвариантом «узел строго выше любого входа»
(`ensureBiggerThan`), в том числе при динамических переподписках `switch` —
там же живёт и детектор циклов зависимостей.

## 4. Задержка `hold`: прошлое доступно, настоящее — нет

Самое контринтуитивное и самое важное правило дискретного FRP (гл. 2, у
Эллиотта то же требование выводится из денотации): **`hold` коммитит новое
значение только на границе момента**. Внутри момента `snapshot` и `sample`
видят значение _до_ него.

```ts
import { newStream } from "@continuum-js/frp";

const [tick, fireTick] = newStream<void>();
const count = tick.accum(0, (_t, n) => n + 1);

// accum внутри устроен как петля hold + snapshot:
//   const acc = out.hold(init)
//   out = tick.snapshot(acc, f)   // snapshot видит ПРЕДЫДУЩЕЕ состояние
fireTick();
console.log(count.sample()); // 1
```

Почему это не причуда, а необходимость: попробуйте определить накопитель без
задержки. `out` зависит от `acc`, `acc` — от `out`; если бы `snapshot` видел
значение _текущего_ момента, определение стало бы нетерминирующим уравнением
`x = f(x)` в тот же миг. Задержка на один момент превращает его в корректную
рекурсию во времени: `состояние(t) = f(событие(t), состояние(t−))`. Книга
называет это «a cell doesn't change until the end of the transaction» и строит
на этом все свои конечные автоматы (state machine pattern): состояние — это
`hold`, переходы — `snapshot` событий по нему.

Тот же паттерн руками, без `accum` — банковский счёт с депозитами:

```ts
import { newStream, Stream } from "@continuum-js/frp";

const [deposit, fireDeposit] = newStream<number>();
const [withdraw, fireWithdraw] = newStream<number>();

const delta = Stream.merge(
  deposit,
  withdraw.map((x) => -x),
  (d, w) => d + w, // одновременные депозит и снятие — одно изменение
);
const balance = delta.accum(0, (d, acc) => acc + d);
```

Следствие для интуиции: **внутри момента прошлое консистентно и целиком
доступно, а настоящее — ещё не существует**. Все читают один и тот же
снимок мира; мир меняется атомарно между моментами.

## 5. `snapshot` против «прочитать в обработчике»

`snapshot` — главный мост от событий к состоянию (гл. 2). Отличие от
привычного «прочитаю переменную в колбэке» — в гарантии одновременности:
значение снимается _в тот же момент_, что и событие, а не «когда обработчик
добежал».

```tsx
// examples/todo, суть: Enter в поле ввода добавляет задачу
const [text, setText] = newBehavior("");
const [submit, fireSubmit] = newStream<void>();

const newTodo = submit
  .snapshot(text, (_s, current) => current.trim())
  .filter((s) => s.length > 0);

const todos = newTodo.accum<string[]>([], (item, list) => [...list, item]);
```

Никакого «а не изменился ли text, пока мы шли» — не изменился, это один
момент. В книге ровно этим приёмом собираются все формы: поле — `Cell`,
кнопка — `Stream<Unit>`, отправка — `snapshot`.

## 6. `switch`: динамический граф (гл. 7)

Всё выше описывает _статический_ граф. `switch` — примитив, которым граф
перестраивает сам себя: behavior, содержащий behavior (или event), и
переключение на текущий внутренний. Книга посвящает ему отдельную главу и
называет «венцом» модели — с ним FRP-сеть становится полноценной программой,
способной выражать создание и удаление частей интерфейса.

```ts
import { newBehavior, Behavior } from "@continuum-js/frp";

// Два независимых счётчика и переключатель между ними
const [counterA] = newBehavior(0);
const [counterB] = newBehavior(100);
const [which, setWhich] = newBehavior<"a" | "b">("a");

const current: Behavior<number> = Behavior.switchB(
  which.map((w) => (w === "a" ? counterA : counterB)),
);
```

Операционно `switch` обязан решить деликатный вопрос: в момент переключения
старый внутренний узел ещё может выстрелить. Правило то же, что у `hold`:
**перекоммутация происходит на границе момента** (наша реализация откладывает
переподписку в фазу `last`, [`Behavior.switchB`](packages/frp/src/index.ts)).
В момент переключения наружу уходит текущее значение нового внутреннего
behavior, а подписка переезжает, когда момент закрыт — старый граф остаётся
живым и консистентным до конца мгновения.

Именно на `switch` держится `<Each>`/`<Dynamic>` в `@continuum-js/dom`:
список строк — это динамическая коллекция под-графов, создаваемых и
уничтожаемых переключением. А известный технический долг ядра — ранги при
`switch` только растут (§14 #6 спецификации, веха v0.6 в
[ROADMAP.md](ROADMAP.md)) — это цена выбранной стратегии `ensureBiggerThan`
при динамической переподписке.

## 7. Операционные примитивы: люки в машинное отделение (гл. 8)

Книга строго делит API на два сорта. **Денотационные** примитивы (десятка из
раздела 2) — чистые, композируемые, с математическим смыслом. И
**операционные** — `listen`, `sample`, `updates` — люки, через которые
FRP-сеть стыкуется с внешним миром. Правило книги: операционные примитивы
живут _на границах_ системы, не внутри логики.

```ts
// ХОРОШО: граница системы (рендерер, лог, сеть)
const un = balance.listen((b) => {
  span.textContent = String(b);
});

// ПЛОХО: логика на колбэках — бедствия из раздела 1 возвращаются
balance.listen((b) => {
  if (b < 0) fireAlarm(); // состояние протекло в императивный мир
});
// ПРАВИЛЬНО: остаться в модели
const alarm = balance.updates.filter((b) => b < 0);
```

В Continuum это правило встроено в архитектуру: единственные легальные
потребители `listen` — рендерер (`@continuum-js/dom` подписывает DOM-привязки;
доставка в фазе `post`, когда момент закрыт) и IO-мост.

### `perform`: IO как данные

У Sodium в книге нет готового примитива для асинхронного IO — гл. 11
обсуждает паттерны стыковки с внешним миром. Continuum оформляет этот паттерн
примитивом:

```ts
import { perform } from "@continuum-js/frp";

const query: Stream<string> = /* ввод пользователя, debounce и т.д. */;
const response = perform(query, (q) =>
  fetch(`/api/search?q=${encodeURIComponent(q)}`).then((r) => r.json()),
);
// Stream<Result<unknown, SearchResults>> — ошибка не исключение, а данные
```

`perform` запускает эффект в фазе `post` (момент запроса уже закрыт), а
результат возвращает в сеть _новым моментом_. Ошибки заворачиваются в
`Result<E, T>` и текут по графу как обычные значения — ветвление
«успех/ошибка» делается `filter`-ом, а не `try/catch`. Поверх `perform` в
`@continuum-js/std` собран `resource` (запрос с состояниями
pending/success/failure) — это FRP-переложение того, что книга в гл. 11 делает
с промисами.

## 8. Одновременность и коалесинг: что происходит при `merge`

Тонкость, которой книга уделяет заметное место (гл. 2, обсуждение
`merge`/`coalesce`): что делать, если в один момент пришли _оба_ входа?
Ответы по нарастанию честности:

1. выбросить один — теряем данные;
2. выстрелить дважды — ломаем денотацию (два происшествия в одно время);
3. **потребовать у вызывающего комбинирующую функцию** — единственно верное.

Поэтому сигнатура — `Stream.merge(ea, eb, combine)`, а `orElse` — это
документированное «левый победил», не умолчание молчком:

```ts
const undoRedo = Stream.merge(
  undoClicks.mapTo("undo"),
  redoClicks.mapTo("redo"),
  (l, _r) => l, // одновременный клик по обеим кнопкам: undo приоритетнее
);
// эквивалент: undoClicks.mapTo("undo").orElse(redoClicks.mapTo("redo"))
```

То же самое внутри одного момента делает `hold`: несколько записей за момент
— побеждает последняя (last-write-wins в пределах мгновения), коммит один.

## 9. Непрерывное время (гл. 9)

Дискретная машина — это _приближение_; денотация `Behavior a ≅ Time → a`
непрерывна. Книга посвящает непрерывному времени гл. 9: behaviors, которые
опрашиваются (pull), а не толкаются, и анимация как функция времени — прямое
наследие Fran. В Continuum:

```ts
import { time, constant, integral, warp } from "@continuum-js/frp";
import { animationFrames } from "@continuum-js/dom";

const now = time(); // Behavior<number>: свежее значение при каждом чтении
const tick = animationFrames(); // Stream<number>: часы кадров

// скорость -> позиция: интегрирование по часам (форвард-Эйлер)
const velocity = constant(120); // px/s
const position = integral(velocity, tick);

// время можно гнуть: всё, что интегрируется по warped-часам, живёт в 2x
const fast = integral(
  velocity,
  warp(tick, (t) => 2 * t),
);
```

Ключевое различие сортов behavior в ядре: у дискретного (`hold`) есть
`updates`, у непрерывного (`fromPoll`) — нет, его читают. `b.map` у нас
специально «continuous-safe»: значение пересчитывается при каждом чтении, а
не кэшируется — иначе непрерывные behaviors врали бы между обновлениями.
Подробнее о следствиях непрерывности — в
[PHILOSOPHY.md](PHILOSOPHY.md#непрерывное-время-и-его-следствия); живой пример
— `examples/animation` (`npm run example:animation`).

## 10. Как закрываются шесть бедствий

Итоговая таблица — бедствие из гл. 1 → механизм модели:

| Бедствие                   | Чем закрыто                                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Непредсказуемый порядок    | внутри момента порядка _нет_ — есть одновременность; протяжка детерминирована рангами                                            |
| Пропущенное первое событие | `Behavior` существует всегда: `b.listen` доставляет текущее значение немедленно; «до подписки» не бывает                         |
| Грязное состояние          | всё состояние — в `hold`/`accum`, изменения атомарны на границах моментов                                                        |
| Реэнтерабельность          | наблюдатели — в фазе `post`, после закрытия момента; `fire` из колбэка открывает новый момент, вложиться нельзя                  |
| Утёкшие колбэки            | `dispose` каскадом отцепляет производные узлы; в `@continuum-js/dom` — дерево владения делает это автоматически                  |
| Случайная рекурсия         | легальная рекурсия — только через задержку `hold` (во времени); мгновенный цикл ловится детектором (`dependency cycle detected`) |

## 11. Где Continuum сознательно отходит от книги

- **Имена** — `Behavior`/`Stream` вместо `Cell`/`Stream`: мы держимся
  терминологии денотационной линии (Fran/Elliott), книга — практической
  (Sodium). Семантика та же.
- **`perform` в ядре.** Книга оставляет IO-стыковку паттернам; мы считаем
  границу IO настолько важной, что она — примитив с фиксированной семантикой
  (запуск в `post`, возврат новым моментом, ошибки как `Result`).
- **`b.map` без кэша.** Sodium может кэшировать значение cell; наш `map`
  пересчитывает при чтении ради честности непрерывных behaviors. Дискретным
  это ничего не стоит: их `updates` уже коалесцированы.
- **Рендерер вместо виджетов.** Книга демонстрирует FRP на Swing/Web-виджетах
  поверх готовых тулкитов; у нас fine-grained DOM-рендерер — сам потребитель
  `listen`, так что прикладной код к операционным примитивам почти не
  прикасается.
- **Известный долг**: устойчивые ранги при интенсивном `switch` (книга эту
  проблему решает M-обходом в Sodium) — у нас в плане v0.6
  ([ROADMAP.md](ROADMAP.md)).

## 12. Два закона движка (нормативные)

Эти два инварианта — не описание текущего поведения, а **контракт**, против
которого проверяется каждая правка ядра. Оба закодированы как оракулы
структурного фаззера (`packages/frp/test/frp.fuzz.test.ts`): фаззер строит
случайные графы, гоняет случайные последовательности операций и сверяет
законы после каждого момента. Нарушение закона — баг по определению, даже
если ни один юнит-тест не падает.

### Закон 1: push ≡ pull

На границе каждого момента значение, доставленное подписчикам (push), равно
значению, которое вернул бы `sample()` (pull). Следствия:

- производная, которую никто не слушает, обязана отвечать на `sample()` так
  же, как отвечала бы с подписчиком (**cold ≡ warm**);
- после ухода последнего слушателя узел не имеет права врать: либо он
  продолжает отвечать честно (формулы пересчитываются, состояние живёт,
  пока живёт его владелец), либо обращение к нему — явная ошибка;
- чистая цепочка без слушателей не потребляет источник (**сон = отцепка**).

### Закон 2: abort = no-trace

Момент, брошенный исключением в любой фазе, бесследен: ни одно состояние,
переживающее момент, — включая **внутренние кэши движка** (стейджинг `hold`,
кэши `combine`, память `distinct`, скип по равенству у ячейки) — не должно
отличаться от состояния до открытия момента. Внутренняя бухгалтерия ядра
обязана соблюдать ту же дисциплину коммита на границе, которую движок
навязывает пользовательскому состоянию.
