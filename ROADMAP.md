# Дорожная карта Continuum

Стратегия развития от «работающего исследовательского фреймворка» к «фреймворку,
которым пользуются в реальных проектах». Версии условные: каждая веха — это
согласованный набор возможностей, а не календарный срок.

Текущее состояние (v0.2): ядро FRP (транзакции, ранги, коалесинг), рендерер
(fine-grained привязки, `each` с LIS, владение, контекст, jsx-runtime),
`@continuum-js/std` (resource, debounce, …), непрерывное время
(`integral`/`derivative`/`warp`), 5 примеров, бенчмарк js-framework-benchmark,
бюджеты size-limit, CI.

Легенда: 🔴 блокер для следующих вех · 🟡 важно · 🟢 желательно

## v0.3 — «Продукт, а не репозиторий» (публикация и DX)

Цель: `npm create continuum` → работающее приложение за минуту. Пока пакеты
нельзя поставить извне монорепо, всё остальное — теория.

### 🔴 Сборка dist и публикация в npm

Сейчас пакеты отдают TypeScript-исходники (`main: ./src/index.ts`) — это
работает только внутри workspace с общим tsconfig.

- [x] Сборка каждого пакета в `dist/` (ESM + `.d.ts`) — plain `tsc` с
      `tsconfig.build.json` (module-preserving, без бандлера; внутренние
      импорты с `.js`-расширениями — dist валиден и для Node ESM);
- [x] `exports` maps на `dist/` с условиями `types`/`import`; поле
      `publishConfig`, `files: ["dist"]`; dev внутри монорепо — через
      `paths` в `tsconfig.base.json` (typecheck не требует dist);
- [x] у `@continuum-js/dom` собрать и субпути `jsx-runtime`/`jsx-dev-runtime`;
- [x] проверка «чистой установки»: `npm run smoke` — pack → установка
      тарболов в чистый Vite-проект → `tsc --noEmit` + `vite build` +
      импорт из Node;
- [x] имя в npm: организация `continuum` оказалась занята → скоуп
      **`@continuum-js`** (организация создана, владелец — denistort);
- [x] версионирование и changelog — `changesets` (fixed-группа frp+dom+std;
      `human-id` запинен из-за ESM-only 4.x);
- [x] GitHub Action `release.yml`: changesets/action ведёт PR «Version
      Packages», его мерж публикует в npm и создаёт GitHub-релизы
      (токен обязан передаваться и как `NODE_AUTH_TOKEN`). Опубликовано:
      `@continuum-js/{frp,dom,std}@0.3.0`.

Критерий готовности: `npm i @continuum-js/dom` в пустом Vite-проекте — и счётчик
из README работает без правок tsconfig.

### 🔴 `create-continuum` — scaffold CLI

- [x] пакет `packages/create-continuum` (`create-continuum-js`, buildless
      ESM без зависимостей), запускается через
      `npm create continuum-js@latest my-app`;
- [x] шаблон: Vite + TS, `jsxImportSource: "@continuum-js/dom"`, готовый

- [x] минимум вопросов (имя проекта аргументом или интерактивно; выбор

- [x] e2e-тест: в `npm run smoke` CLI генерирует проект во временную папку,
      зависимости подменяются на локальные тарболы → `npm i` →

### 🟡 Гигиена API перед публикацией

Публикация фиксирует контракт — дешевле навести порядок до неё.

- [x] аудит публичного API всех трёх пакетов: движковые методы

## v0.4 — «На этом можно писать SPA» (роутер)

Цель: маршрутизация как первоклассный житель FRP-модели. URL — это буквально
`Behavior<Route>`; это самая выигрышная демонстрация подхода.

### 🔴 `@continuum-js/router`

- [x] `location(): Behavior<URL>` поверх History API (popstate + `navigate`;
      ленивый синглтон — импорт без побочных эффектов);
- [x] матчер путей: статика, `:id`, wildcard (`params["*"]`), многосегментные
      пути, слияние параметров вниз по цепочке; чистая функция `matchChain`;
- [x] `<Router>` поверх `dyn`: динамическая область ключуется ИДЕНТИЧНОСТЬЮ
      определения маршрута — навигация `/users/1 → /users/2` не пересобирает
      страницу, обновляется только behavior параметров;
- [x] вложенные маршруты и layout'ы (`<Outlet>`), контекст маршрута через
      `createContext`; pathless-layout'ы рендерят детей насквозь;
- [x] ленивые страницы: `lazy(() => import("./Page"))` — литеральный
      динамический импорт в коде пользователя → отдельный чанк у бандлера
      (проверено `vite build`); pending/error как данные, модуль кэшируется
      (без `resource` из std: его нумерация запросов для одноразового
      импорта избыточна);
- [x] `<Link>` с активным классом (точное совпадение для `/` и при `end`),
      скролл к верху при push-навигации;
- [x] guard'ы как чистые функции `params → true | путь-редиректа`
      (redirect — replace-навигацией, не засоряет историю);
- [x] пример `examples/router-app`: вложенный layout, реактивные параметры
      со счётчиком построений, ленивая страница отдельным чанком, guard, 404.

Попутно роутер вскрыл и починил два бага ядра `dyn` (level-triggered рендер
против устаревших доставок при реентерабельных моментах; уборка региона по
диапазону маркеров против осиротевших узлов вложенных динамических областей).

Критерий готовности — ✅ закрыт `examples/router-app` (решение от 2026-07-06:
отдельное переписывание todo в SPA не делаем): многостраничное приложение без
хаков, back/forward работает (popstate-тест), владение уничтожает поддерево
ушедшей страницы (тест на `onCleanup`), ленивый чанк реально отделяется при
`vite build`. **Веха v0.4 закрыта**: роутер (3.8 kB brotli со всеми
зависимостями, бюджет 4 kB) + тест-утилиты.

### 🟡 Тест-утилиты `@continuum-js/test`

Понадобятся и нам (роутер тестировать), и пользователям.

- [x] `render(view)` → `{ container, dispose }` с автоочисткой между тестами

## v0.6 — «Ядро без оговорок» (устойчивость)

Цель: закрыть известные долги ядра, из-за которых сейчас нужны оговорки.

### ✅ Изоляция ошибок рендерера (error boundaries)

- [x] семантика определена: ловятся ошибка `build`-фазы (children — thunk) и
      ошибка пересборки вложенного динамического региона; ошибки в `map`
      привязок не ловятся (держите их чистыми), ошибка fallback'а
      эскалирует к внешней границе;
- [x] `<Catch fallback={(error, reset) => …}>`: уничтожает владение
      упавшего поддерева (включая частично построенное), показывает
      fallback, умеет `reset`;
- [x] ошибки post-фазы (`perform`/`resource`) приходят данными (`Result`/
      `Async`) — задокументировано в JSDoc `Catch` и гайде;
- [x] тесты: построение, обновление, восстановление, эскалация, отсутствие
      утечек; попутно TDD вскрыл и закрыл баг ядра — `Behavior.listen`
      терял обновление, выпущенное во время первичной доставки.

### ✅ Устойчивые ранги при `switch` (§14 #6)

- [x] воспроизводящие тесты: мёртвые `targets` источника (1000 записей за
      1000 циклов), остаточная инфляция ранга после глубокой цепочки,
      цикл-через-время между двумя switch;
- [x] стратегия выбрана и записана в PHILOSOPHY.md («Решение: устойчивость
      рангов»): рефконт `targets` + ребейз switch к живой топологии вниз +
      детекция циклов (мгновенная после чистки targets; страховочный
      `RANK_LIMIT = 2^16` для темпоральных). Полный пересчёт и
      ordered-ranks отвергнуты — дороже без выигрыша на живых DAG;
- [x] реализация + бенчмарк до/после: в пределах шума (create 1k ≈ 29 ms,
      partial ≈ 19.7 ms на обеих ветках).

### 🟡 Долгосрочная устойчивость

- [x] стресс-тест на утечки: детерминированный слой в CI (счётчики
      слушателей/таймеров/узлов: 10k mount/unmount, 10k переключений Show,
      20k строк Each) + heap-слой `npm run stress` (--expose-gc через
      poolOptions, 12k циклов, порог 5 MB). Нашёл и закрыл реальную утечку
      ядра: публичный `listen` не завершал каскад отцепления производных —
      каждая привязка к переживающему компонент значению текла. Введён
      `retain()` для намеренно долгоживущих модульных производных;
- [x] property-based тесты транзакционных инвариантов (fast-check,
      `frp.properties.test.ts`): отсутствие глитчей на случайных ромбах,
      коалесинг merge, задержка hold (snapshot видит прошлое), порядок фаз
      (post-наблюдатель видит закоммиченное), accum ≡ функциональной
      свёртке — всё против чистой модели на случайных цепочках;
- [x] аудит `each`: семантика дубликатов детерминированная — «первое
      вхождение побеждает», строка живёт одна на ключ и не перестраивается;
      зафиксировано четырьмя тестами (`dom.each-duplicates.test.tsx`),
      поведение совпадает с задокументированным в доке списков.

## Чем НЕ занимаемся (и почему)

- **Компилятор/билд-тайм-трансформ.** Ключевое решение фреймворка — Behavior
  как значение делает трансформ ненужным. Не отказываемся от него ради
  синтаксического сахара.
- **Сравнительные бенчмарки других фреймворков внутри репо.** Пробовали —
  честного сравнения в кустарной обвязке не получается (см. историю PR).
  Правильный путь — заявка в официальный krausest/js-framework-benchmark
  после публикации в npm (v0.3).
- **Совместимость с React-экосистемой хуков.** Модель принципиально другая;
  мимикрия под хуки размоет главную идею.

## Сквозные принципы

- Каждая веха заканчивается публикуемым релизом (после v0.3).
- Прогон бенчмарка локально до/после изменений ядра; бюджеты size-limit —
  жёсткие, расширение бюджета — осознанное решение в PR.
- TDD: красный тест раньше кода, включая воспроизведение багов.
- Новые возможности приходят с примером в `examples/` и страницей в доках
  (после v0.5).
