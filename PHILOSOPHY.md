# Идея FRP, на которой стоит Continuum

Разложим модель целиком — от философии до алгебры и последствий. Речь о
*классическом* FRP в смысле Конала Эллиотта, том самом, на котором построен наш
[`@continuum/frp`](packages/frp/src/index.ts).

---

## Суть: программирование времени, а не перерисовки

FRP отвечает на вопрос «как *декларативно* описать значения, меняющиеся во
времени». Обычный императивный код описывает время через мутации и обработчики:
«когда случился клик — поменяй переменную — перерисуй». FRP переворачивает это:
ты описываешь, чем величина *является как функция времени*, а не какими шагами её
обновлять. Отсюда родословная — Fran (1997, Elliott & Hudak), система для
анимации, где всё естественно параметризовано временем.

Ключевая методологическая установка Конала — модель **денотативная**: у каждого
типа есть точный математический смысл (денотация), и каждая операция определяется
через этот смысл, а реализация лишь верно его приближает. Это не украшение — из
денотации выводятся и корректность, и сами операции.

---

## Два примитива и их денотации

Вся модель держится на двух типах:

```
Behavior a  ≅  Time → a          -- значение в каждый момент времени (континуум)
Event a     ≅  [(Time, a)]       -- список происшествий, упорядоченный по времени
```

**Behavior** — величина, которая существует *всегда*: позиция мыши, текущее
время, температура. Определена над `Time = ℝ` (вещественные числа), то есть
непрерывна по своей природе. Модель считывания — **pull**: спрашиваешь значение
в нужный момент.

**Event** — поток дискретных происшествий, каждое в свой момент: клики, нажатия,
приходящие сообщения. Между происшествиями «ничего нет». Модель — **push**:
происшествие само проталкивается тем, кто на него подписан.

Разделение на эти два вида — не техническая деталь, а сердце модели. Непрерывное
(что *есть*) и дискретное (что *случается*) — фундаментально разные вещи, и
попытка выразить одно через другое (как в сигналах/стримах) теряет либо
непрерывность, либо честную семантику моментов.

---

## Алгебра: какие это структуры

Красота в том, что примитивы — не просто контейнеры, а известные алгебраические
структуры, и операции из этих структур и вытекают.

**Behavior — это Applicative Functor.**

- `fmap :: (a → b) → Behavior a → Behavior b` — поточечно: `fmap f b = \t -> f (b t)`.
- `pure a` — константа во времени: `pure a = \t -> a`.
- `(<*>) :: Behavior (a → b) → Behavior a → Behavior b` — тоже поточечно:
  `(bf <*> bx) t = (bf t) (bx t)`.

Именно `<*>` позволяет поднять обычную функцию на меняющиеся во времени
аргументы: `lift2 (+) mouseX mouseY` — сумма двух движущихся величин, сама
движущаяся величина. В нашем коде это `Behavior.apply` / `lift2` / `lift3`.

**Event — это Functor + Monoid.**

- `fmap` — преобразовать значение каждого происшествия (`map`).
- фильтрация (`filter`), пустое событие `never` (нейтральный элемент), слияние
  `merge` (моноидальная операция).

Само время — тоже величина: `time :: Behavior Time`, `time t = t`. Из неё
строится всё остальное (`fmap sin time` и т.п.).

## Мосты между непрерывным и дискретным

Отдельно — операции, сшивающие два мира; они и делают модель выразительной:

```
stepper  :: a → Event a → Behavior a               -- держать последнее значение (у нас: hold)
snapshot :: Event a → Behavior b → Event (a,b)     -- замерить поведение в момент события
accum    :: a → Event (a→a) → Behavior a           -- свернуть происшествия в состояние
switcher :: Behavior a → Event (Behavior a) → Behavior a  -- переключать поведения (switchB)
```

`stepper`/`hold` — главный мост: превращает дискретный поток в непрерывную
ступенчатую величину. `switcher` — это уже **higher-order FRP**: поведение,
значениями которого являются другие поведения; событие переключает, за каким из
них следить. Это то, что даёт динамические, перестраивающиеся графы (у нас
`switchB`/`switchE`).

## Денотационный дизайн как метод

Конал не просто *даёт* смысл — он требует, чтобы инстансы были **гомоморфизмами
смысла** (type class morphisms): значение `fmap f` должно равняться `fmap f`,
применённому к значению. То есть «смысл композиции = композиция смыслов».
Сначала пишешь денотацию, потом реализацию, которая ей верна по построению. Это
и отличает FRP-по-Коналу от «просто реактивных» библиотек, задаваемых
операционно («вот как оно крутится внутри»).

## Непрерывное время и его следствия

Раз `Time = ℝ`, а не «тики», из модели бесплатно вытекают вещи, недоступные
дискретным системам:

- **Интеграл и производная.** `integral :: Behavior Vector → Behavior Vector`.
  Движение по ускорению, физика, сглаживание — почти даром. В сигналах/стримах
  так чисто это не выразить.
- **Time warping** — можно преобразовать само время: `b . (\t -> 2*t)` —
  прокрутить поведение вдвое быстрее.
- **Независимость от разрешения** — семантика не знает о частоте кадров; она
  появляется только на этапе семплирования при рендере. Одну и ту же анимацию
  можно отрендерить в 30 или 120 fps без изменения описания.

## Реализация: push-pull

Отсюда статья Конала 2009 года *Push-Pull FRP*. Проблема: непрерывные behaviors
хотят **pull** (спрашивать значение по требованию), а события — **push**
(реагировать в момент). Решение — разбить реактивное поведение на «реактивную»
часть (постоянна до следующего события — её можно push-ить) и непрерывную
(функция времени — её надо pull-ить). Именно этот раскол в нашем ядре: `Event`
толкается по графу, `Behavior.sampleNoTrans` считывается; ступенчатые behaviors
имеют и то и другое (`updates` для push, `sample` для pull), непрерывные —
только pull.

## Чем это НЕ является (важная для Конала граница)

По его меркам **сигналы (Solid) и стримы (RxJS) — не FRP**: у них дискретное
время (тики/эмиссии, а не континуум) и нет простой денотации — они заданы тем,
«как работают». Он называет это реактивным/событийным программированием и просит
не звать это FRP; сам предлагал более честное имя — *denotative continuous-time
programming*. Различие не в снобизме: без непрерывного времени теряются интеграл,
time warping и независимость от разрешения; без денотации теряется выводимость
операций и их законов.

## Как это соотносится с тем, что мы собрали

Честно: наш [`@continuum/frp`](packages/frp/src/index.ts) — **дискретная ветвь**
традиции (стиль Sodium: `Behavior` = «Cell», транзакции, ранги, glitch-free,
`hold` с задержкой в конце момента). Это корректный и практичный FRP по структуре
— те же два примитива, та же алгебра, те же мосты. Непрерывное время у нас есть
(`integral`/`derivative`/`warp`), но оно **численно семплируется** по дискретному
клоку, а не является первоклассной величиной над `Time = ℝ`; и операции мы
задавали конструктивно (транзакции, ранги), а не выводили из формальной
денотации. То есть по форме — FRP, по букве Конала — его прикладная,
дискретно-семплируемая версия.

| | Continuum (мы) | Чистый Конал (Fran/reactive) |
|---|---|---|
| Примитивы | `Event` + `Behavior` | `Event` + `Behavior` |
| Время | дискретные моменты + семплирование | континуум `Time = ℝ` |
| `integral` / `derivative` | есть (численно, forward Euler) | есть (аналитически) |
| Time warping | есть (`warp` над клоком тиков) | есть (над осью времени) |
| Задание операций | конструктивно (транзакции, ранги) | вывод из денотации |
| Независимость от fps | описание — да; результат — приближение | полная |

«Чистая» ветвь теперь видна на работающем коде: `integral`/`derivative` над
behaviors и `warp` (замена временнóй оси) реализованы в ядре и живут в демо
[`examples/animation`](examples/animation). Отличие от Конала — численность и
зависимость от частоты клока (пункт #7 дорожной карты в [README](README.md)).
